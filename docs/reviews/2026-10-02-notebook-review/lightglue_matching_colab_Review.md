## Executive assessment

The default experiment is sound and unusually honest. Two upstream checkpoint pickles are digest-verified, statically
audited, converted once to safetensors and loaded strictly into vendored networks; 360 digest-pinned CC0 photographs
become exact-reference homography pairs split by photograph; the frozen matcher is read beside three baselines on
the same 96 test pairs, per tier; and the adaptation is selected on validation, not test. The exact blob under review
has a documented clean-runtime Kaggle T4 run whose numbers match the notebook's claims within expected variation.

Three problems stop it being ready. **Run all does not complete in one pass**: the same Kaggle record shows the install
cell raising its restart guard (cuda-bindings 12.9.4 → 13.4.2, numpy 2.0.2 → 2.5.3), and the run passed only after
the executor restarted the kernel, yet README, STATUS and the tutorials index call it Release-grade. **The documented
optional experiments and the BYOD re-run both continue from the already-adapted matcher**: `pipe.adapt` has no reset to
the base, so a re-run labels an adapted model's validation score "frozen model", stacks training, and writes an
adapter manifest that does not mention the earlier run (direct CPU execution, P04). Seven Minor findings cover the BYOD
size claim (8 stated, 24 needed), template text defects, hard-coded build-record numbers that contradict the recorded
run, evidence and spec-version gaps, a hard assertion that can abort learner experiments before export, a thin
guided-learning layer, and silent multi-minute CPU stages.

No finding here says the recorded default-path numbers are wrong.

## 2. Separate judgments

**Technical correctness.** Strong on the default path: pinned identity carried twice and asserted, digest checks before
any deserialisation, static pickle audit, strict loads, transactional `adapt`, digest-checked adapter with an exact
tensor set, leakage check by decoded pixels. Two defects: the in-kernel install cannot complete Run all in one pass on
the recorded hosted image (LGC-M1), and Section 7 is not re-entrant — re-running it continues from adapted weights
(LGC-M2, LGC-M3). The reload-parity check compares counts and `kpts1` only (LGC-S1).

**Promise fulfilment.** The default promises are delivered and evidenced by the exact-blob Kaggle run, apart from "Run
all … needs no … intervention" (LGC-M1). The optional-experiment and BYOD promises are not delivered as stated: the
experiments do not compare against the frozen matcher they claim to (LGC-M2), BYOD re-run scores an adapted model as
its frozen baseline (LGC-M3), and "at least eight" photographs is really 24 (LGC-m1).

**Learner experience.** The prose is accurate, explains score semantics, baselines, leakage and the limits of
synthetic warps well, and tells the learner that keeping epoch 0 is a valid outcome. But the numbers it quotes as what
happened are one CPU replay's, not this run's, and one of them has the opposite sign in the recorded run (LGC-m3); the
learner meets 245 KB of carried code with no "Infrastructure" label; there are no predictions, checkpoints,
troubleshooting or conclusion prompts, and the only experiments are prose (LGC-m6); the default CPU path has
multi-minute stages with no progress output (LGC-m7).

**Spec conformance.** Unresolved applicable `MUST`s: RUN1, RUN10, ENV6, REL2/REL11 (LGC-M1); SRC2, VER5, OUT8, ART8
(LGC-M2); DAT13, DAT14, OUT8 (LGC-M3); DAT12 (LGC-m1); SRC3 (LGC-m2); REL12 (BYOD never verified, LGC-m1). Several `SHOULD`s in the GDL family (LGC-m6).

## 3. Findings

### LGC-M1 — Major: Run all stops at the install cell; the Release-grade run needed a restart

- **Cell/section:** Section 1, cell 3 (generator: `tools/build_notebook.py` install-cell template; prose in
  `tools/notebook_template.py` Section 1 text).
- **Observed issue:** The cell pip-installs `torch==2.14.0`, `numpy==2.5.3` and three other pins into the running
  kernel, then raises `RuntimeError(... Restart the runtime, then rerun from the top.)` when an already-imported
  distribution changed. On the recorded hosted image it did exactly that.
- **Consequence:** A learner choosing Run all in a fresh runtime stops at the first code cell and must restart and
  re-run by hand. `docs/release-verification.md` step 4 calls the restart "expected", while README.md, STATUS.md and
  `tutorials/README.md` call the notebook Release-grade on the strength of that restart-assisted run.
- **Evidence:** Documented execution evidence, exact blob: Kaggle `run_summary.json` pass 1 `ok: false` with
  `cuda-bindings: loaded=12.9.4, installed=13.4.2; numpy: loaded=2.0.2, installed=2.5.3`; pass 2 ok after
  `restarted_after_install_cell: true`. Source inspection of cell 3.
- **Recommended correction:** Replace the in-kernel install with the fleet's uv isolated-environment pattern: a carrier
  cell bootstraps uv, creates `uv venv --managed-python --python 3.12.12 <ROOT>/env`, installs a hash-locked
  requirements file with `uv pip install --require-hashes --only-binary :all:`, and runs the workload in that env so the
  kernel's preloaded NumPy/torch are never replaced (reference:
  `ast-audio-classification-pipeline/tutorials/DIMER_Sound_Event_Classification_Workshop.ipynb` on `origin/main`).
  Until a one-pass run is recorded, return the status token to Candidate in README.md, STATUS.md and
  `tutorials/README.md`, and drop "an interpreter restart … is expected" from release-verification step 4.
- **Acceptance check:** A fresh hosted runtime (Colab, or the Kaggle T4 image) executes every code cell of the new blob
  in order in one kernel with no error output and no restart, recorded with blob, runtime and outcome in
  `docs/release-verification.md`; the three status documents agree with that record.
- **Spec:** RUN1, RUN10, ENV6, REL2, REL11.

### LGC-M2 — Major: The optional experiments re-run fine-tuning on the already-adapted matcher

- **Cell/section:** Interpretation cell 32 "Optional experiments" (`tools/notebook_template.py:528`); Section 7 cell 27;
  `LightGluePipeline.adapt` (`src/lightglue_pipeline/pipeline.py:437`).
- **Observed issue:** The experiments ("set `TRAINABLE_LAYERS = 4` …; raise `EPOCHS` …; change `LEARNING_RATE` to
  `1e-5` and read a smaller, steadier change") can only be run by re-running Section 7 on the same `pipe`. `adapt`
  trains whatever weights the matcher currently holds and always labels its epoch 0 "frozen model"; Section 8 then
  compares the twice-adapted model against the original `frozen_test`.
- **Consequence:** The learner reads a cumulative effect as the effect of the one changed variable; "epoch 0 = frozen"
  is false; the "smaller, steadier change" at `1e-5` is measured on top of the default run's change; the exported
  adapter manifest records only the last call's configuration and history, so the artifact cannot be interpreted.
- **Evidence:** Direct execution (CPU, real weights, stand-in sizes; P04): after a 2-layer run, the `TRAINABLE_LAYERS =
  4` re-run reported epoch 0 "frozen model" at validation precision 0.528 against 0.510 for a fresh base on the same
  pairs; the manifest says `trainable_layers 4, epochs 1`, no prior adaptation. Source inspection of `adapt` (no base
  restore before training; `initial_state` is the current state). Whether the effect is material at the default
  schedule is inferred, not measured.
- **Recommended correction:** Make each Section 7 run start from the pinned base: either rebuild the pipeline at the
  top of the cell (`pipe = LightGluePipeline.from_pretrained(weights_dir=WEIGHTS_DIR)`) or add a `reset_to_base()` used
  by the cell, re-score `frozen_test` when the base is reloaded, and turn the prose experiments into an explicit
  rerun instruction ("re-run Sections 7–9"). Optionally have `adapt` refuse to start on an adapted matcher unless told
  to continue, and record `continued_from` in the adapter manifest.
- **Acceptance check:** Running Section 7 twice in one kernel (default, then `TRAINABLE_LAYERS = 4`) gives a second
  epoch-0 validation score equal to a fresh base's; the second artifact's manifest describes only training from the
  base; Section 8's delta is relative to the base.
- **Spec:** SRC2, VER5, OUT8, ART8, GDL10.
